# 티켓타카 (TicketTaka)

문화생활 티켓을 기록하면, 그 이력으로 사용자 취향을 분석해 작품을 추천하는 서비스.
데이터사이언스캡스톤디자인(DSCD) 팀 프로젝트 — 팀 NOVI.

> 포지셔닝: "기록 앱"이 아니라 **문화생활 이력 데이터 기반 사용자 취향 분석 및 개인화 추천**이 핵심.
> 기능을 추가·수정할 때 항상 "이게 취향 분석/추천 품질에 어떻게 기여하나?"를 기준으로 판단할 것.

## 기술 스택

| 영역 | 사용 기술 |
|---|---|
| 백엔드 | Django |
| 프론트엔드 | React |
| DB | PostgreSQL (개발·배포 모두. SQLite 쓰지 않음) |
| 영화 데이터 | TMDB |
| 공연(뮤지컬·연극) 데이터 | KOPIS |
| 전시 데이터 | 문화공공데이터광장 API_CCA_145(전국 국공립 박물관·미술관) + 서울 열린데이터광장 문화행사(전시/미술) |
| 작품 태깅 | GROQ API의 LLM |
| 티켓 인식 | PaddleOCR + Gemma 4 |

## 자주 쓰는 명령어 (Backend 폴더에서 실행)

```bash
cd Backend
python manage.py runserver
python manage.py makemigrations && python manage.py migrate
python manage.py test
```

- DB 접속 정보는 `.env`에서 읽는다. SQLite는 쓰지 않는다.
- **작품 DB는 박서현 PC의 PostgreSQL 하나를 팀 전체가 같이 쓴다** (2026-10-30). 팀원은 Tailscale로 접속한다 (`DB_HOST`=박서현 PC의 Tailscale IP).
  - 그래서 `migrate`는 박서현만 한다. 모델을 바꿀 때는 팀에 먼저 알린다.
  - 작품 데이터는 지금 DB에 있는 것이 최종본이다. CSV로 내보내거나 나눠 갖지 않는다.
- 새벽 작업: `data/daily.bat` (Windows 작업 스케줄러 "TicketTaka daily tagging")이 공연·전시 수집 → 줄거리 보충 → 장르·느낌 태깅 → 인기도 갱신 → 작품 묶기를 한다. 영화는 새로 수집하지 않고 인기도만 갱신한다.
- 작품 이미지: `Work.image_url`·`Production.image_url` (2026-10-30, 프론트 요청). 영화 TMDB 포스터(w500) / 뮤지컬·연극 KOPIS 포스터 / 전시 문화공공데이터광장 `IMAGE_OBJECT`·서울시 `MAIN_IMG`. 새 작품은 수집할 때 같이 받고, 이미 있던 작품은 `fill_images`로 한 번 채웠다. 이미지는 주소만 저장하고 파일은 받지 않는다.
- 환경 변수는 `.env` 하나로만 관리한다. (`.env.example`은 만들지 않음) 새 환경 변수를 추가하면 팀원에게 키 이름을 따로 알려 줄 것.

## 서비스 범위

- **작품 카테고리: 영화, 뮤지컬, 연극, 전시** 네 가지를 다룬다. (이전 4개 카테고리 계획에서 축소 → 2026-10-16 연극 추가 → 2026-10-18 전시 추가)
  - DB에서 연극은 뮤지컬과 별도 카테고리(`play`)로 둔다. 수집·줄거리 보충·장르 태깅·인기도는 뮤지컬과 같은 방식.
  - KOPIS id는 공연(지역·시즌·극장) 단위라서, 제목이 같은 공연은 작품(`Production`) 하나로 묶는다 (`group_performances`, 2026-10-18). 추천은 작품 단위로 한다.
    - 작품마다 **가장 최근 공연 하나만 남기고 나머지 공연은 지운다** (2026-10-18). 작품의 장소·출연진은 그 공연 것, 기간은 첫 공연 시작일 ~ 마지막 공연 종료일. 지운 공연의 원본 ID는 `Production.source_ids`에 남겨서 다시 수집하지 않고, 예매 순위도 그 작품에 연결한다.
    - 공연이 하나도 안 남은 작품은 지우지만, **`source_ids`가 빈 작품은 지우지 않는다** (2026-10-20). 공연(KOPIS) 없이 직접 넣은 작품이라서다 (예: 팀원 CSV로 받은 뮤지컬 M05160~M05178).
    - 작품마다 번호(`Production.code`)를 붙인다: `M00001` 뮤지컬 / `P00001` 연극 / `E00001` 전시. 첫 공연 시작일 순으로 붙였고, 한 번 붙은 번호는 바뀌지 않는다. 새 작품은 다음 번호.
  - 전시(`exhibition`)도 추천 대상이다 (2026-10-18 결정). 칼럼은 뮤지컬·연극과 똑같다 (`actors`=작가, `plot`=설명).
    - 전시도 작품(`Production`)으로 묶는다. 뮤지컬과 달리 `[..]`를 지우지 않고 제목 전체로 묶는다 (전시 이름이 `[..]` 안에 있는 경우가 많음). "특별전"처럼 이름이 없는 제목은 묶지 않는다.
    - 한국 전시의 일본어·중국어판(대한민국역사박물관·국립한글박물관이 언어별로 따로 올린 것)은 다루지 않는다 (2026-10-24). 수집할 때 거르고(`is_foreign_exhibition`), 이미 있던 88개는 지웠다. "百濟瓦當 特別展"처럼 한자 제목의 한국 전시는 남긴다.
    - 설명이 없으면 네이버 검색으로 채운다 (`fill_plots`). 전시는 제목이 같아도 다른 전시가 많아서 다른 전시 설명을 빌려 오지 않는다.
    - 장르·느낌은 뮤지컬·연극과 같은 방식으로 태깅한다 (2026-10-19). 인기도는 아직 빈 칸이다.
    <!-- TODO: 전시 인기도 출처 팀 확인 (KOPIS 예매 순위 같은 공공 데이터가 전시에는 없음) -->
  - 영화는 **TMDB 인기도 2 이상**만 다룬다 (2026-10-27 결정). 2 미만 72,552편을 지웠다 (115,153편 → 42,601편).
    - 새 영화는 더 수집하지 않는다 (2026-10-30). 인기도만 매일 갱신하고, 나중에 2 밑으로 떨어져도 자동으로 지우지 않는다.
- 콘서트, 페스티벌, 스포츠, 무용·국악·클래식은 다루지 않는다. 콘서트·페스티벌은 추천·설문·기록 어디에도 쓰지 않는다 (2026-10-20 결정).
- **하지 않기로 한 것** (제안하지 말 것):
  - 동행 매칭
  - 콘텐츠 기반 추천 (줄거리 유사도만으로 추천하는 방식)
  - 비슷한 다른 사용자 기반 협업 필터링
  - 측면 기반 감성 분석(ABSA)
  - 별점 입력
  - **티켓 이미지 저장** — 인식 후 이미지는 저장하지 않는다.

## 주요 기능

1. 회원가입 + 취향 설문
2. 티켓 기록 (사진 → OCR 인식 → 사용자 확인 → 만족도 입력)
3. 작품 추천 (카테고리별 1개씩: 영화·뮤지컬·연극·전시 각 1개)
4. 인생작 입력 (5개)
5. 관람 후기(선택), 마이티켓 통계
6. (부가) 문화관람자 유형 진단, 커뮤니티

## 핵심 도메인 규칙

### 1. 가입 설문
- 카테고리별로(영화 / 뮤지컬 / 연극 / 전시 따로) 세 가지 요소의 1~3순위를 고른다.
  - 영화: 장르 · 배우 · 감독
  - 뮤지컬: 장르 · 출연진 · 장소
  - 연극: 장르 · 출연진 · 장소
  - 전시: 장르 · 작가 · 장소 (2026-10-20 확정)
- 순위를 ROC 값으로 바꿔 **요소 중요도 초기값**으로 쓴다: 1순위 0.61 / 2순위 0.28 / 3순위 0.11
- 사용자가 막대(슬라이더)로 수치를 직접 조정할 수 있다.
- 인생작 5개를 입력받는다.

### 2. 티켓 기록과 만족도
- 사용자 확인 단계에서 위 세 요소 각각에 **좋아요 / 보통 / 싫어요**를 필수로 받는다.
- 배우(출연진)는 여러 명을 보여주고 각각 고르게 한다. **고르지 않은(모르는) 배우는 점수 계산에서 제외.**
- 전시 작가도 똑같이 여러 명을 보여주고 각각 고르게 한다. **고르지 않은(모르는) 작가는 점수 계산에서 제외.**
- 관람 후기는 선택. 텍스트마이닝으로 좋았으면 가산, 싫었으면 감점 — 요소별이 아니라 **작품 전체**에 적용하고 비중은 작게.
- 점수 크기:
  - 일반 기록: ±2점
  - **추천받은 작품을 보고 기록한 경우: ±3점** (북마크 여부와 상관없이, 좋아요·싫어요 모두)
- **시간 가중치**: 최근 기록일수록 크게 반영 (1주일 전 > 3개월 전 > 6개월 전 > 1년 전).
- 출연진(영화 배우·뮤지컬/연극 출연진)은 영화·뮤지컬·연극 사이에서 **방향 구분 없이 똑같이** 연결해 반영한다.
- 전시 작가 점수는 **전시 추천에만** 쓰고, 영화·뮤지컬·연극 출연진과 연결하지 않는다 (2026-10-20 결정). 이름만으로 연결하면 동명이인이 한 사람으로 묶이기 때문.

### 3. 작품 태깅 (2층 구조)
- 1층: 장르 / 2층: 분야를 넘나드는 "느낌" 태그
- 1층 장르
  - 영화: TMDB 장르를 그대로 쓴다. (줄거리도 TMDB 것만 쓰고, 네이버로 보충하지 않음)
  - 뮤지컬·연극: KOPIS 줄거리를 보고 **LLM으로 태깅**. KOPIS 줄거리가 없으면 네이버 검색 결과로 보충한다.
    - 뮤지컬 장르: 드라마, 로맨스, 코미디, 스릴러, 미스터리, 공포, 판타지, SF, 액션, 범죄, 역사, 가족
    - 연극 장르: 드라마, 코미디, 블랙코미디, 로맨스, 스릴러, 공포, 추리, 판타지, 역사극, 고전극, 아동극
    - 프롬프트 틀은 같고 장르 목록·설명·예시만 다르다 (`works/tagging.py`).
  - 전시: 설명(문화공공데이터광장·서울시 문화행사, 없으면 네이버)을 보고 **LLM으로 태깅** (2026-10-19). 이야기가 아니라 무엇을 보여 주는지(매체·주제)로 나눈다.
    - 전시 장르: 회화, 조각·설치, 사진, 미디어아트, 공예·디자인, 일러스트·캐릭터, 건축, 고미술, 역사, 민속·생활문화, 과학·자연, 어린이·체험
    - "현대미술"(대부분에 붙어서 구분이 안 됨), "기획전·특별전·개인전"(전시 여는 방식일 뿐 내용이 아님)은 장르로 쓰지 않는다.
    - 작가·장소·설명을 프롬프트에 넣으므로 공연과 프롬프트를 따로 둔다 (`EXHIBITION_GENRE_PROMPT`).
- 2층 느낌: 작품마다 태깅하지 않고, **장르마다 LLM에 한 번씩** 물어서 정한다.
  - 작품에는 자기 장르들의 느낌을 합쳐서 붙인다. 겹치는 느낌은 한 번만. (예: 드라마 → 감동적인, 따뜻한 / 로맨스 → 설레는, 낭만적인 → "드라마+로맨스" 작품은 감동적인, 따뜻한, 설레는, 낭만적인)
  - 같은 장르면 영화·뮤지컬·연극·전시 상관없이 같은 느낌이 붙는다. 느낌 목록도 모든 분야가 같은 것을 쓴다.
  - 장르가 없는 작품은 느낌도 없다.
- 태깅 결과는 공유 DB에 바로 넣는다.
- 줄거리 기반 취향 벡터에 기록 작품을 섞을 때, **장르에 싫어요를 준 기록은 넣지 않는다.**

### 4. 추천
- **인기 기반 + 사용자 취향 기반** 두 가지를 섞는다.
  - 사용자 취향 기반 = 가입 설문 + 본인의 관람 이력·만족도로 만든 개인 취향. **추천의 중심 축.**
  - 인기 기반 = 가입 직후(콜드스타트)용. 기록이 쌓일수록 비중을 줄인다.
- 둘을 섞는 비율 β는 수집한 사용자 데이터(약 50명)로 **BPR 학습**, **NDCG@5**로 최종 선택.
- 쏠림 방지: **카테고리별 1개씩** 추천. 뮤지컬과 연극도 따로 1개씩 → 영화·뮤지컬·연극·전시 총 4개.
- 추천은 **사용자가 티켓을 기록할 때만** 갱신한다. (그래서 "최근 추천 작품 N일 제외" 같은 규칙은 쓰지 않음)

## 작업할 때 지켜줄 것

- 설명은 **수식·수학 기호 대신 쉬운 말과 구체적인 예시**로.
- 추천 로직이나 DB 구조를 바꾸는 제안은, 바로 고치기 전에 **위 "핵심 도메인 규칙"과 충돌하는지 먼저 확인**하고 충돌하면 알려줄 것.
- "하지 않기로 한 것" 목록에 있는 방식은 먼저 제안하지 말 것.
- 임의로 숫자(가중치, 유형 개수 등)를 정하지 말 것 — 교수님 피드백: 근거 없이 정한 값 대신 "데이터 → 방법 → 결과 분석 → 적용" 흐름으로 정할 것. 정해지지 않은 값은 `TODO`로 남기고 물어볼 것.
- API 키는 코드에 직접 쓰지 말고 `.env`로 관리.
